# Architecture

How Rot Royale fits together, and why the parts that look arbitrary are shaped the way they are.

This is the document to read before changing anything. It is organised around the properties the
system has to keep rather than around the directory tree — the tree is discoverable, the properties
are not, and most of them were learned by breaking something.

---

## 1. What the game is

A **windowed-async skill contest**. The ranked event is the **Daily Royale**: one eight-question run
per Eastern-time day, inside a 24-hour window, scored against everyone else who played that day.

A contest is an ordered list of **round modules**. Everything else — streaks, the campaign, the
vault, duels — is packaging around those eight questions.

There is no real money, no payments and no gambling. Two in-game currencies, both closed-loop and
earned-only: **coins** (spendable; campaign and practice earn them, the vault spends them) and
**gems** (scarce; Daily Royale placement and streak milestones grant them).

---

## 2. The invariants

Seven properties the codebase is built to preserve. Each has a section below. If a change breaks
one, the change is wrong — or the invariant needs an explicit, argued revision.

| # | Invariant | §  |
|---|-----------|----|
| 1 | Answers never leave the server; client scores are never trusted | [§4](#4-round-modules-and-the-anti-cheat-split) |
| 2 | Coins and gems move only through their append-only ledgers | [§8](#8-currency-ledgers) |
| 3 | Window times are computed in ET via `zoneinfo` — never a hardcoded UTC offset | [§6](#6-windows-timezones-and-dst) |
| 4 | Schema changes only via Alembic — never `create_all`, never hand-edited | [§3](#3-stack-and-layout) |
| 5 | Placement, rating, gems and share links describe real entries only | [§7](#7-settlement) |
| 6 | Player-facing copy carries no money framing and never an invented count | [§10](#10-copy-honesty) |
| 7 | The server must never require a client change | [§11](#11-two-release-trains) |

## 3. Stack and layout

**Backend** — FastAPI, async throughout, PostgreSQL via SQLAlchemy 2.x async, Alembic for schema,
JWT auth, APScheduler (or platform cron) for the window scheduler and settlement jobs. Dependencies
are managed with `uv` against a committed lockfile.

```
backend/app/core        config, security, db session, timezone helpers
backend/app/models      SQLAlchemy models
backend/app/schemas     Pydantic request/response models
backend/app/api         routers
backend/app/modules     round modules + registry
backend/app/services    contest engine, scoring, settlement, ledgers
backend/app/jobs        scheduler and worker entrypoints
backend/content         content loading, ingestion and validation
```

**Frontend** — Vite + React + TypeScript, one codebase for web and for the Capacitor-wrapped iOS and
Android builds. Zustand holds session and UI state; screens fetch through a typed client in
`src/api/client.ts`.

```
frontend/src/app        shell and routing
frontend/src/screens    screens
frontend/src/modules    round modules + registry (mirrors the server's)
frontend/src/theme      theme tokens
frontend/src/ui         shared motion/UI primitives
frontend/src/i18n       localised copy
```

**Schema changes go through Alembic and nothing else** *(invariant 4)*. Never `create_all` against a
real database, never hand-edit schema. Autogenerated migrations routinely include unrelated drops —
read every generated migration and trim it to the intended change before applying it.

**Screens are code-split, and the shell is the only thing on the cold-start path.** Every screen
reached from an app-level flag goes through `src/app/lazyScreens.ts`, home's tap-opened overlays
through `src/screens/home/lazyOverlays.ts`, and the public legal routes through `main.tsx` — each
behind a single `<Suspense>`. Statically importing a screen into `App.tsx`, `Home.tsx` or `main.tsx`
folds it back into the initial chunk; that is how the bundle once became a single 645 KB `main`.
Locale dictionaries split the same way: one non-English dictionary is fetched on demand and held in
the store, so the translation hook stays synchronous.

## 4. Round modules and the anti-cheat split

**Adding a game mode means adding a module. The contest engine is never touched.** Both sides
register in a registry keyed by `type`.

The core of it is one function signature:

```
generate(rng, difficulty, ctx) -> (client_spec, server_answer)
```

- `client_spec` goes to the client and **must never contain the answer**. For trivia that means the
  prompt and the options, and not `correctIndex`.
- `server_answer` is stored server-side only and is what `score()` reads.

*(Invariant 1.)* The client submits a result; the server's `score(server_answer, submission)` is
canonical. A client-reported score is display-only and is ignored entirely. The client cannot reveal
correctness mid-round because it does not have the answer — correctness comes back on submit.

`score()` returns a judgement of `{correct, time_frac, valid, flags}` — **not points**. The module
judges; the scoring service prices.

**`correctIndex` is positional.** It indexes the options array exactly as sent. Reordering options
without moving the index silently corrupts the question, and nothing will catch it for you.

### Scoring lives in one place

```
points = correct ? round((100 + time_frac * 60) * (1 + min(streak, 5) * 0.12)) : 0
```

`streak` counts consecutive correct answers **within the contest** and is incremented before the
multiplier, so the first correct answer is streak 1 and scores ×1.12.

`time_frac = clamp((limit_ms - elapsed_ms) / limit_ms, 0, 1)` using the **server's** `limit_ms`. The
client's `elapsed_ms` is clamped and never trusted.

### Submission is module-agnostic

Each round's submission carries an opaque `result` dict. The submit endpoint maps index to result
and the module reads its own fields, so adding a module never touches submit, engine or scoring.

### Interactive rounds

Most modules are atomic: one generate, one submit. Two cognition types — Fermi **estimate** (three
guesses, narrowing) and **change detection** (spot the difference between two frames) — are
interactive, and one-shot generate/score cannot hold their turn-by-turn state. They own a separate
round instance bound to `(entry, round index)`, are played through their own endpoints, and are then
finalised once through the normal answer endpoint, which **bridges** their outcome onto
`(correct, time_frac)` and into the single scoring formula above. There is deliberately no second
economy.

Their anti-cheat rules are per type. An estimate's answer *and its components* — which would let a
client derive it — stay server-side until the round resolves; feedback is a direction and a
close/far band. Change detection's bounding box is server-only and expressed in **normalised 0–1
coordinates with tolerance as a fraction of the image dimension**, so screen size can never change
difficulty.

## 5. Determinism and seeding

`build_round_set(seed, template, ctx)` is a **pure function**: same inputs, same rounds. An entry is
regenerable from its stored `seed`, and the stored round set is an audit copy rather than the source
of truth. The content bank is fetched in a stable order because the seed indexes into it.

**Which seed depends on the mode, and the difference is deliberate.**

The ranked Daily Royale uses a **shared per-window seed** derived from the contest date and slot.
Every player that day gets the identical eight questions in the identical option order — Wordle-style
— which is the property that makes a leaderboard and a "beat my score" share meaningful.

This reverses an older per-entry seed, and the trade-off is explicit: a shared seed is leakable
within the 24-hour window. That is acceptable because the contest is currency-only and
server-validated — answers still never leave the server, and client scores are still ignored.

**Every other mode keeps a per-run seed.** Practice, category sessions, campaign and duels are not
leaderboard-comparable, so they keep their variety.

## 6. Windows, timezones and DST

Get this wrong and every window drifts by an hour for roughly eight months of the year.

One daily contest, defined in **wall-clock America/New_York**:

| Slot   | Opens (ET) | Closes (ET)     | Settles (ET)     |
|--------|------------|-----------------|------------------|
| royale | 12:00 AM   | 12:00 AM next day | 12:15 AM next day |

A full 24-hour window: open all day, midnight to midnight ET, and the player takes their one run
whenever they like. A `close_is_next_day` flag means the close time is read on the following
calendar date, so on a DST-change date the window is genuinely 23 hours (spring forward) or 25 hours
(fall back).

Rules *(invariant 3)*:

- Compute every window time in `America/New_York` with `zoneinfo`.
- **Never hardcode a UTC offset.** `-05:00` and `-04:00` are both wrong for most of the year.
- Store instants as UTC `timestamptz`, *computed from* the ET wall-clock definition for each date.
- Time **labels** in the UI are viewer-local — the client formats the UTC instant in the viewer's own
  timezone. This never conflicts with the above: ET defines *when* the window opens, the UI shows
  that instant wherever the player is.

State transitions (`SCHEDULED → OPEN → CLOSED`) are driven by a scheduler tick and applied lazily on
read as a defensive fallback. **Settlement is never lazy** — see below.

## 7. Settlement

`settle_window` ranks submitted entries (score descending, then faster average `time_frac`), applies
the rating change and division, advances the daily streak, writes standings, and marks the window
settled.

- **Gated, never lazy.** Settlement runs only once `now >= settle_at`. A transition may be applied on
  read; a settlement may not.
- **Exactly-once and atomic.** It locks the window row and acts only if the state is `CLOSED`, and it
  never commits — the worker commits once, so the settled flip and every profile and standing write
  land in a single transaction. Safe under multiple instances.
- **The streak keys off the window's contest date, not settlement wall-clock.** The window closes at
  midnight and settles at 12:15 AM the *next* date; keying off the clock would break every streak.
- **Guests are excluded** from ranking, rating, streak, standings and gems. Leaderboard permanence
  needs a saved profile. Play paths are never gated.
- **Ranked pays no coins.** Coins are earned in campaign and practice and spent in the vault.
  Settlement grants gems only, all idempotency-keyed so a re-settle never double-grants.

### Where synthetic entrants may and may not appear

*(Invariant 5.)* This is a boundary rather than a blanket ban, and the boundary is the design.

A two-person day renders as a podium with an empty third step and no rows beneath it, which reads as
a broken screen rather than a quiet one. So the **live** board of a thin day is topped up with
deterministic fillers while the window is open.

Everything that outlives the window is real:

| Surface | Fillers |
|---|---|
| The live board, window open | **allowed** — a provisional view that is replaced when the window closes |
| Settlement: placement, rating, gems, streak, standings | forbidden — nobody is paid for beating a filler |
| Public share links | forbidden — "3rd of 8" outlives the window and must mean eight real people |
| The underlying field read | forbidden — the honest read stays honest |

The padding lives in exactly one function, called from the field **endpoint** only, and deliberately
not from the field read itself — so every other caller, present or future, gets real entries unless
it opts in explicitly. A test pins each boundary in both directions, because a rule nobody tests is
a rule that drifts.

Two details keep even the provisional view honest. A filler's score is computed through the same
`compute_points` formula as a human's, so it can never post a number a real run could not reach. And
fillers carry no earned cosmetics — frames, badges and titles are proof of something a player
actually did, so hanging one on an invented entrant would be a second and worse fiction.

A solo day settles as 1st of 1 and moves no rating, rather than inventing an opponent. Duel rivals
are a separate thing entirely — an explicit, disclosed 1v1 practice partner the player chose to
face, never a leaderboard entrant and never counted in a field size.

## 8. Currency ledgers

Both ledgers are **append-only and are the source of truth** *(invariant 2)*. Every movement is an
immutable row with a reason and a reference. `coins_balance` and `gems_balance` on the profile are
**caches that must always equal their ledger sum**.

**Never mutate a balance without writing a ledger row.** There is exactly one chokepoint per
currency, and zero-value writes are skipped so the ledgers never carry no-op rows.

The gem ledger adds two guarantees the coin ledger does not have:

- **Idempotency** — a one-time grant passes a stable key; a repeat returns the existing row and
  writes nothing. Enforced by a partial unique index and made race-safe with a savepoint.
- **Non-negative balance** — a debit that would drive the balance below zero raises and writes
  nothing.

Services never commit. The request boundary commits once.

## 9. Rot Rating

The headline profile "sharpness" number. It is **parallel to the placement rating** used for
divisions and gems, and the two must never be merged: placement rating answers "how did you do
against the field today", Rot Rating answers "how sharp are you, independent of who else showed up".

It is a Glicko-2 implementation validated against Glickman's published worked example. It is never
labelled or described as IQ anywhere player-facing.

**Each round is one opponent, scored pass/fail.** One eight-round run is one rating period of eight
games, and the update fires at run completion — independent of the field and of settlement. Guests
are excluded, for the same reason they are excluded from settlement: a rating needs a saved profile.

**Speed never enters Rot Rating.** Points reward speed; Rot Rating measures sharpness. Two numbers,
two jobs, and letting them collapse into one would leave neither meaning anything. That is precisely
why a round contributes only its pass/fail, and not its `time_frac`.

**The rating-deviation floor is deliberately high**, so the number visibly moves after a strong run.
That trades precision for responsiveness on purpose, and it is a value to retune downward once real
distributions exist rather than a constant to leave alone forever. Because the deviation never drops
below the floor, "provisional" keys off rounds played rather than off the deviation.

**Three sub-ratings** — one per verb (notice, estimate, know) — each updated only from that verb's
rounds. The headline is **derived**: a precision-weighted mean of the sub-ratings that were actually
played, so it can never disagree with its own parts, and an unplayed verb's prior never drags it.

**Item difficulty sits behind a resolvable key**, so today's coarse per-band difficulty can become
per-item later without a rewrite. Trivia difficulties are a **fixed anchor** and never converge —
they are the stable reference scale the rest is measured against. Only the two floating verbs
converge on observed pass rate, in a once-daily batch that then re-centres each pool to its seed
mean, so a strong cohort cannot inflate players and items together.

That batch is **not idempotent** — game counts accumulate — so it claims its day exactly once
through an insert-on-conflict marker, making a redundant or mistimed run a clean no-op. It must
never be folded into the frequent heartbeat job.

## 10. Copy honesty

Mandatory in any player-facing string *(invariant 6)*:

- Coins and gems are never framed as cash, prizes, bets or jackpots, **in any language**. The banned
  lists live in `frontend/src/i18n/copyGuard.ts` and are enforced by tests across every locale and
  against rendered markup.
- "Windowed" and "open until", never broadcast-live. No fake chat, no concurrent-viewer counts.
- **No fabricated number, in any wording.** Settled placements and share links count real entries
  only, so "3rd of 8" on a shared result means eight people played. The live in-progress board is the
  one padded surface ([§7](#7-settlement)), and it is provisional by construction — it is replaced by
  the real field the moment the window closes.
- Localisation is compile-enforced: the dictionary type is derived from the English one, so every
  other locale must supply every key or the build fails. Server error **codes** map to localised
  text on the client — a raw server string is never rendered to a player.

This is also why a crowd-prediction round type was removed before launch rather than shipped. It
scored against crowd share and needed roughly 300 responses per prompt to be real; at launch scale
every round would have been graded against a seeded distribution presented as a real crowd. It
needed traffic it could only get by shipping dishonest first.

## 11. Two release trains

**The server must never require a client change** *(invariant 7)*.

The web app updates the moment you deploy. The iOS and Android binaries update when the app stores
say so, and every installed app is running whatever web bundle was frozen into it. **The oldest
binary in the wild — not the current source — is the compatibility floor.**

Two rules follow, and both were learned from a live outage in which every symptom was silent:

**Widen inputs freely; never narrow them.** A change-detection timeout field was tightened from "any
coordinate" to 0..1, but shipped binaries send `(-1, -1)` to mean "timed out, no tap". The resulting
422 left the round unresolved and stranded players mid-run. The server still accepts the legacy
sentinel and will until the installed base turns over.

**Never change a response shape a shipped client already parses.** Where a new behaviour must change
what an endpoint returns, put it behind a request flag that older clients cannot set, and default
that flag off. A trivia second-chance feature withheld a result the old binary depended on; the old
binary read the offer as an ordinary reveal, advanced, and then wedged on the next round's sequence
guard — a white screen, mid-run, with no recovery. Native binaries cannot be rolled back.

A third consequence is easy to miss: **relative asset URLs resolve against the app bundle.** Capacitor
loads the web build from disk, so `/assets/foo.jpg` is looked up *inside the binary*, not on the
server. Content added after a binary shipped simply 404s there, with nothing in any log to notice.
Anything a shipped client cannot resolve has to be resolved for it, server-side, as an absolute URL.

**The service worker must never run inside the native app.** On the web it is the PWA. Inside the
native wrapper it earns nothing — the build is already on disk — and it is what would break
over-the-air updates, because the bundled build and any live-updated build share one origin. A
worker precaching `index.html` would keep serving the old one and its old hashed chunk names, so the
update either silently never applies or the app white-screens on chunks that no longer exist.

## 12. The content boundary

This repository contains the engine. The production question corpus, campaign data,
change-detection imagery and most artwork live in a separate private package.

**Production refuses to boot without an explicit content root.** There is deliberately no fallback:
silently serving placeholder questions into a ranked contest would be worse than not starting. In
any non-production environment the app reads a committed sample corpus instead, so a fresh clone
runs.

The deployment fetches the private package at build time, pinned to a **full immutable revision**,
and validates it before installing it. The validation's strongest check rebuilds derived data and
compares it byte-for-byte with what the package committed, so a package whose inputs and outputs
disagree is rejected rather than deployed.

**Release identity is a pair.** The application revision and the content revision are logged
together at startup, because either can change without the other. Content is baked into the build
artifact rather than mounted at runtime, which is what makes a rollback restore the matching content
rather than leaving new content under old code.

### Content rules that survive the boundary

- **Ingestion is review-gated.** Files are human-reviewed before ingestion; valid rows land as
  `approved`. Only `approved` and `live` rows are ever served, so staged content cannot reach a
  player. Malformed rows are rejected loudly with a reason and never silently dropped.
- **Upsert on (question, category).** A row whose content changed is refreshed in place; status is
  preserved so a promoted row is never demoted by a re-ingest. Note that editing a question's *stem*
  changes the key, so it inserts a new row and orphans the old one.
- **Categories are a closed set.** Ingest rejects any category outside the canonical tuple, so a typo
  cannot spawn a near-duplicate category. Adding one is a deliberate edit.
- **Translations never touch the canonical payload.** Localised text is served through a separate
  `display` dict; the English payload stays canonical because campaign keys hash it. A translation
  whose option count has drifted from the source is refused rather than served — `correctIndex` is
  positional, so serving it would remap the answer onto a different-length list. Fallback is per
  question, so a partly translated bank still serves a complete round.

## 13. Working on it

### Verification gates

"Done" means you ran these and they passed.

| Change touches | Must pass |
|---|---|
| Backend logic | `uv run ruff check .` · `uv run ruff format --check .` · `uv run mypy app` · `uv run pytest` |
| Frontend logic | `npm run typecheck` · `npm run lint` · `npx vitest run` |
| Anything visual | the frontend three, plus looking at the running app at mobile width |
| Production surface | `npm run build` — it catches what dev mode hides |
| Database schema | a migration, `uv run alembic upgrade head`, and the backend suite |

Report what you ran and what it said. A failing test reported honestly is worth more than a passing
claim. A green CI tick is not a substitute: a pull request's checks ran against the base commit it
was opened on, so if the main branch has moved, re-verify the merged result rather than the branch
in isolation.

The backend suite runs against a real PostgreSQL inside a per-test transaction that is rolled back,
so nothing persists — which works only because services never commit. Migrate the database first;
the harness uses the existing schema and does not create tables.

### Measure rather than eyeball

Tuning a value against artwork means reading the image's pixels — alpha, rims, bounding boxes — and
deriving the number, not nudging until it looks close. Tuning layout means querying the live DOM for
real rectangles. Claiming data is present or missing means querying it. A value you can justify from
a measurement survives the next redesign; leave the derivation in a comment beside it.

### A note on images

Assets in `public/` are **not** content-hashed by the bundler, so re-exporting art under the same URL
leaves every browser that already fetched it serving the old bytes forever. Bump the version query
on the token when you replace one.

Ship art at roughly 3× its measured render size rather than at master resolution. The image payload,
not the JavaScript bundle, is the bottleneck on this app — the home screen once pulled 1.78 MB to
paint 37–46 px avatars, about fifteen times the size of the entire bundle.

WebP is deliberately not used. The iOS project targets a deployment version whose WKWebView predates
WebP support, so adopting it would silently break every image for those users. Raising the
deployment target is the prerequisite, not a detail to skip.
